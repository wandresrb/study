<Lead>
Ordenar una tabla por otra columna, filtrar una galería por categoría, mover una tarea de una columna a otra: son las tres interacciones donde una lista salta de golpe y el usuario pierde de vista el elemento que estaba mirando. Es el caso en que FLIP aporta más valor por línea de código, porque el problema que resuelve no es estético sino cognitivo: mantener la continuidad de identidad de los objetos cuando su posición cambia. Y es también el caso donde aparecen los elementos que entran y salen, que es la parte del plugin que casi nadie configura bien.
</Lead>

<Objetivos>

- Animar una reordenación completa de lista con una sola captura.
- Manejar el filtrado con `onEnter`, `onLeave` y `absoluteOnLeave`.
- Correlacionar elementos con `data-flip-id` cuando los nodos se recrean.
- Usar `prune` y `stagger` juntos sin producir huecos temporales.

</Objetivos>

## Reordenar

Una reordenación es el caso más limpio: los mismos elementos, en distinto orden. Ni entran ni salen.

```html
<div class="controles">
  <button data-orden="nombre">Por nombre</button>
  <button data-orden="precio">Por precio</button>
</div>
<ul class="lista">
  <li class="item" data-nombre="Teclado" data-precio="89">Teclado</li>
  <li class="item" data-nombre="Monitor" data-precio="240">Monitor</li>
  <li class="item" data-nombre="Raton" data-precio="35">Raton</li>
  <li class="item" data-nombre="Silla" data-precio="310">Silla</li>
  <li class="item" data-nombre="Lampara" data-precio="52">Lampara</li>
</ul>
```

```js
import { gsap } from "gsap";
import { Flip } from "gsap/Flip";

gsap.registerPlugin(Flip);

const lista = document.querySelector(".lista");

document.querySelectorAll("[data-orden]").forEach((boton) => {
  boton.addEventListener("click", () => {
    const items = gsap.utils.toArray(".item");
    const estado = Flip.getState(items);
    const clave = boton.dataset.orden;

    items
      .slice()
      .sort((a, b) =>
        clave === "precio"
          ? Number(a.dataset.precio) - Number(b.dataset.precio)
          : a.dataset.nombre.localeCompare(b.dataset.nombre)
      )
      .forEach((item) => lista.appendChild(item));

    Flip.from(estado, {
      duration: 0.55,
      ease: "power2.inOut",
      stagger: 0.03,
      absolute: true,
    });
  });
});
```

Funciona pegado tal cual. La reordenación se hace con `appendChild` en el orden nuevo, que mueve cada nodo al final; aplicado en secuencia, deja la lista ordenada. Es la operación de DOM más barata para esto y no destruye ningún nodo, así que las identidades se conservan y Flip no necesita ayuda.

`absolute: true` es lo que evita el efecto de "empujón" mientras los elementos se cruzan. Y el `stagger` pequeño convierte un movimiento simultáneo en uno que el ojo puede seguir.

## Filtrar: los que entran y los que salen

Filtrar es distinto porque hay elementos que dejan de estar y elementos que aparecen. Para Flip, "no estar" significa `display: none` o no existir en el DOM.

Un elemento que estaba en la captura y no está en el estado final no tiene geometría de destino, así que no puede formar parte de la animación de posición. Un elemento que aparece de nuevo no tiene geometría de origen. Para ambos hay callbacks dedicados.

```js
const contenedor = document.querySelector(".galeria");

function filtrar(categoria) {
  const estado = Flip.getState(".pieza");

  gsap.utils.toArray(".pieza").forEach((pieza) => {
    const visible = categoria === "todo" || pieza.dataset.categoria === categoria;
    pieza.style.display = visible ? "" : "none";
  });

  Flip.from(estado, {
    duration: 0.5,
    ease: "power2.inOut",
    absolute: true,
    absoluteOnLeave: true,
    prune: true,
    stagger: 0.03,
    onEnter: (elementos) =>
      gsap.fromTo(elementos, { autoAlpha: 0, scale: 0.85 }, { autoAlpha: 1, scale: 1, duration: 0.4 }),
    onLeave: (elementos) =>
      gsap.to(elementos, { autoAlpha: 0, scale: 0.85, duration: 0.3 }),
  });
}
```

Tres detalles hacen que esto funcione y no son opcionales.

`absoluteOnLeave: true` saca del flujo a los que se van. Sin él, un elemento con `display: none` no se ve, y por tanto la animación de salida que devuelves en `onLeave` no se ve tampoco. Con la opción activa, Flip fuerza el `display` anterior durante la animación y lo saca del flujo para que no descoloque a los demás.

Las animaciones que **devuelves** desde `onEnter` y `onLeave` se añaden a la timeline del FLIP. Eso importa: si una transición se interrumpe por otra, esas animaciones se fuerzan al final junto con el resto en lugar de quedarse colgadas a medias.

`prune: true` descarta los elementos que no se han movido, y en un filtrado hay muchos: los que ya estaban visibles y siguen en la misma posición. Sin él, el `stagger` los cuenta y produce pausas donde no ocurre nada.

<Callout type="tip" title="display: none frente a quitar del DOM">
Ambas cosas funcionan con Flip. `display: none` es más barato y conserva las identidades, así que es lo que quieres para un filtro que se va a alternar muchas veces. Quitar del DOM libera nodos y es mejor para listas muy largas, pero entonces los elementos que vuelvan serán nodos nuevos y necesitarás `data-flip-id` para correlacionarlos.
</Callout>

## Cuando los nodos se recrean

Si tu lista se renderiza desde datos —cualquier framework moderno, o un `innerHTML` a mano— la reordenación no mueve nodos: los destruye y crea otros. El estado capturado sigue teniendo la geometría correcta, pero apunta a nodos que ya no existen, y Flip no anima nada.

La solución tiene dos partes y hay que poner las dos.

La primera es `data-flip-id` en cada elemento, con un identificador estable —el identificador del dato, no el índice—. Flip lo usa para casar cada elemento del estado con su equivalente actual. Si no lo pones, el plugin asigna identificadores automáticos incrementales, que sirven para nodos que sobreviven pero no para nodos recreados.

La segunda es `targets` en `Flip.from()`, que le dice al plugin sobre qué elementos actuales debe aplicar el estado. Sin eso, usa por defecto los del estado, que son los viejos.

```js
// La lista se re-renderiza entera desde datos
const estado = Flip.getState(".item");

lista.innerHTML = datos
  .sort(comparador)
  .map((d) => `<li class="item" data-flip-id="${d.id}">${d.nombre}</li>`)
  .join("");

Flip.from(estado, {
  targets: ".item",   // los nodos NUEVOS
  duration: 0.5,
  absolute: true,
});
```

Y hay una condición temporal: en frameworks que renderizan de forma diferida, la fase Last no ha terminado cuando tú crees. Hay que esperar a que el DOM esté actualizado antes de llamar a `Flip.from()`. En React eso es un `useLayoutEffect`; a pelo, un `requestAnimationFrame` de un tick suele bastar. La documentación menciona además `Flip.batch()` para el caso de varios componentes independientes que deben capturar todos antes de que ninguno cambie.

## Coordinar varios: Flip.batch

Cuando dos zonas de la página van a cambiar a la vez y son código independiente, hay un problema de orden: si la primera aplica su cambio antes de que la segunda haya capturado su estado, la segunda captura una geometría ya contaminada.

`Flip.batch(id)` devuelve un objeto que coordina las tres fases: primero se ejecutan todas las capturas, después todos los cambios, y después todas las animaciones.

```js
const lote = Flip.batch("reorganizar");

lote.add({
  getState: () => Flip.getState(".columna-a .tarea"),
  animate: (self) => Flip.from(self.state, { duration: 0.5, absolute: true }),
});

lote.add({
  getState: () => Flip.getState(".columna-b .tarea"),
  animate: (self) => Flip.from(self.state, { duration: 0.5, absolute: true }),
});

// Ejecuta las tres fases en el orden correcto
lote.run();
```

<Callout type="dios" title="Animar una reordenación no es decoración: es la única forma de que el usuario no pierda el objeto que estaba mirando">
Existe una tentación razonable de tratar esto como un lujo: la lista se reordena igual de bien saltando, así que la animación es un adorno. Esa lectura ignora para qué sirve el movimiento aquí. Cuando pulsas "ordenar por precio", tu atención está puesta en un elemento concreto —el que estabas evaluando— y la pregunta que tienes en la cabeza no es "¿cuál es el orden nuevo?" sino "¿dónde ha ido a parar el mío?". Con un salto instantáneo esa pregunta solo se puede responder releyendo la lista entera, porque el sistema visual no tiene forma de establecer correspondencia entre dos configuraciones que aparecen sin transición: no hay señal que le diga que el tercer elemento de antes es el séptimo de ahora. Con una transición continua, el mecanismo perceptivo de seguimiento de objetos hace ese trabajo solo y sin esfuerzo consciente; es el mismo mecanismo que te permite seguir a una persona concreta entre una multitud en movimiento y que falla por completo si esa multitud parpadea y reaparece recolocada. Por eso la duración importa más de lo que parece y por eso las transiciones muy rápidas fallan a su propósito: por debajo de unos doscientos milisegundos el seguimiento no se establece y el resultado se percibe casi igual que un salto, con la desventaja añadida de parecer un fallo. Y por eso el `stagger` tiene un límite superior: si el escalonado total supera medio segundo, el usuario deja de ver un reordenamiento simultáneo y empieza a ver una secuencia de movimientos independientes, con lo que la relación entre el orden viejo y el nuevo vuelve a perderse. La conclusión operativa es que en este caso concreto el parámetro de duración no se elige por gusto: se elige para que quepa en la ventana en la que el sistema visual puede mantener la correspondencia, que empieza alrededor de los 250 milisegundos y se acaba alrededor de los 700.
</Callout>
