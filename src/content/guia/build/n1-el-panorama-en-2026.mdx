## Vite, el sustrato común

Vite ganó el desarrollo. En su versión 8 no es solo una herramienta que eliges: es la base sobre la que se construyen casi todas las demás. Aprender Vite no es aprender una opción entre muchas, sino aprender el sustrato compartido de todo el frontend moderno.

Buena parte del ecosistema se apoya en él:

- **Meta-frameworks:** Astro, Nuxt, SvelteKit, SolidStart y React Router usan Vite para su dev server y su build.
- **Herramientas:** Storybook para componentes y Vitest para tests comparten el mismo motor y la misma configuración.
- **Plugins:** un ecosistema compatible con la API de Rollup que se reutiliza en todos ellos.

Esa reutilización tiene una consecuencia práctica: la configuración es casi la misma en todas partes. Un `vite.config.ts` que entiendes en un proyecto Astro se lee igual en uno de SvelteKit o en la config de Vitest.

```ts
// vite.config.ts: la misma forma reaparece bajo casi todos los frameworks
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [],
  build: { target: "es2022" },
});
```

La pieza que consolida ese papel es la **Environment API**, que generaliza la dualidad dev/build a múltiples entornos de ejecución: el mismo proyecto puede tener un entorno de cliente, uno de SSR en Node y otro para el edge o un worker, cada uno con su configuración, todos orquestados por el mismo Vite. Es la infraestructura que los meta-frameworks necesitaban para dejar de reinventar la rueda cada uno por su lado.

<Callout type="info" title="Aprender Vite es aprender la plataforma">
Cuando una herramienta se vuelve el sustrato de tantas otras, dominarla tiene un efecto multiplicador. La configuración, los plugins y los conceptos de Vite reaparecen, casi idénticos, dentro de Astro, de SvelteKit o de Vitest. El tiempo que inviertes en entender su modelo mental se amortiza en cada framework que se construye sobre él, que en 2026 son prácticamente todos.
</Callout>

## El toolchain se reescribe en Rust

La primera revolución de velocidad la trajo Go con esbuild. La segunda, más profunda, la está trayendo Rust.

La diferencia no es solo un lenguaje más rápido: es la ambición de unificar bajo un mismo núcleo herramientas que hasta ahora eran islas separadas. Donde antes había cuatro programas que apenas se hablaban, empieza a haber uno solo con muchas caras.

<Cards>
  <Card icon="🦀" title="Rolldown 1.0">
    Un bundler compatible con la API de Rollup, escrito en Rust y construido sobre Oxc. Se convierte en el bundler único de Vite: sustituye a esbuild para pre-empaquetar y a Rollup para producción.
  </Card>
  <Card icon="⚙️" title="Oxc">
    El Oxidation Compiler: parser, resolver, transformador, `oxlint` y `oxfmt`, todo en Rust y compartiendo un mismo AST. Sustituye a ESLint y Prettier con mejoras de 50 a 100 veces.
  </Card>
  <Card icon="⚡" title="SWC y Turbopack">
    SWC, también en Rust, transpila dentro de Next; y Turbopack, de Vercel, es su apuesta de bundler. La misma tesis desde otra casa.
  </Card>
  <Card icon="🧰" title="Biome">
    Un linter y formateador en Rust en una sola herramienta, alternativa integrada a la pareja ESLint más Prettier. Otra señal de la corriente de fondo.
  </Card>
</Cards>

La idea que lo articula todo es la del **AST compartido**. Tradicionalmente, tu código se parseaba una y otra vez, una por herramienta:

- El linter parseaba para encontrar problemas de estilo.
- El formateador parseaba para reescribir el código.
- El transpilador parseaba para transformar la sintaxis.
- El bundler parseaba para construir el grafo.

Cuatro parsers distintos, cuatro representaciones del mismo archivo, el mismo trabajo repetido cuatro veces. Oxc rompe ese desperdicio construyendo un único árbol sintáctico que linter, formateador, transformador y resolver reutilizan. Parsear una vez y reusar muchas es donde nacen buena parte de esas mejoras de dos órdenes de magnitud.

```bash
# El toolchain en Rust, ejecutandose donde antes iban ESLint y Prettier
oxlint .          # linting en milisegundos
oxfmt --write .   # formateo sobre el mismo AST
# y por debajo de Vite 8, Rolldown como bundler unico
```

En la capa de paquetes, la misma pulsión por la eficiencia la encarna **pnpm 11**, con su almacén direccionable por contenido que evita duplicar dependencias en disco, sus workspaces para monorepos y sus catalogs para fijar versiones compartidas. Rapidez y ausencia de repetición, el mismo lema, una capa más abajo.

Ese mecanismo de catalogs se declara una vez y lo hereda todo el monorepo, de modo que actualizar una versión es cambiar una sola línea:

```yaml
# pnpm-workspace.yaml: una version compartida por todos los paquetes
catalog:
  vite: ^8.0.0
  vitest: ^3.0.0
```

## Hacia dónde va todo

El vector es claro: **convergencia**. Se puede resumir en pocas líneas de dirección:

- **Menos herramientas:** un núcleo en Rust reemplaza a un mosaico de utilidades sueltas en JavaScript.
- **Vite como interfaz:** Rolldown unifica su interior, que dejará de coordinar esbuild y Rollup para hablar con un solo motor.
- **Los extremos se separan:** el buildless gana en lo simple gracias al ESM nativo, y el caching de Turborepo y Nx domina a escala.
- **La interfaz se estabiliza y el motor se sustituye:** por eso puedes cambiar de motor sin reescribir tu configuración.

Ese último punto es la clave para orientarte. En todo el stack conviene separar lo que perdura de lo que se reemplaza:

- **Interfaces (perduran):** ESM, la API de Vite, la API de plugins de Rollup, la línea de comandos de tus herramientas.
- **Motores (se reemplazan):** esbuild, Rollup, Rolldown, Oxc, SWC; el que hoy es el más rápido y mañana será otro.

<Callout type="dios" title="Apuesta por las interfaces, no por los motores">
Hay un patrón que se repite en toda esta historia y que, una vez lo ves, te ordena el ruido de las novedades: la industria estabiliza interfaces y reemplaza motores. La interfaz de módulos es ESM, y no ha cambiado aunque por debajo la resolución la haya hecho Node, esbuild o ahora Oxc. La interfaz de bundler es la API de Rollup, y Rolldown la reimplementa en Rust sin que tus plugins ni tu configuración se enteren. La interfaz de desarrollo es Vite, y su motor ha pasado de JavaScript a Go y de Go a Rust mientras tu `vite.config.ts` seguía intacto. Esta es la lección estratégica de todo el track: cuando decidas dónde invertir tu tiempo de aprendizaje, apuesta por las interfaces —ESM, la API de Vite, la de Rollup—, porque perduran, y trata los motores —esbuild, Rolldown, Oxc, el que venga— como piezas intercambiables que mejoran solas sin pedirte nada. Quien aprende motores persigue una cinta que no para; quien aprende interfaces se sube a la parte de la torre que no se mueve. En un ecosistema que se reescribe en Rust cada pocos años, saber qué es cimiento y qué es andamio es la diferencia entre reaprenderlo todo cada temporada y capitalizar lo aprendido década tras década.
</Callout>
