<Lead>
Un plugin es solo código Lua que Neovim carga desde el runtimepath. Un gestor lo clona, lo actualiza y fija su versión. Desde 0.12 el editor trae el suyo propio —`vim.pack`— y lazy.nvim sigue vivo y siendo el rey de la carga perezosa. La pregunta interesante ya no es cuál eliges: es qué plugin va en cada sitio.
</Lead>

<Objetivos>

- Instalar, actualizar y borrar plugins con `vim.pack`, el gestor integrado en 0.12.
- Versionar el lockfile nativo y reproducir tu editor exacto en otra máquina.
- Saber qué aporta lazy.nvim que el gestor nativo no, y a qué precio.
- Montar una configuración híbrida donde los dos convivan sin pisarse.

</Objetivos>

## El falso dilema

Casi todo lo que leerás por ahí plantea esto como una elección excluyente: "¿lazy.nvim o `vim.pack`?". Es una pregunta mal hecha. Los dos son gestores de Git con una capa de Lua encima, los dos dejan los plugins en directorios del runtimepath, y **pueden convivir en la misma configuración sin problema**.

La diferencia real está en la capa de arriba. `vim.pack` responde a "instala esto y mantenlo en esta versión". lazy.nvim responde además a "…y no lo cargues hasta que pase tal cosa", que es otro problema distinto. La mayor parte de una configuración no necesita esa segunda respuesta.

## vim.pack: el gestor que ya tienes instalado

No hay bootstrap, no hay clonado inicial, no hay nada que descargar: es una función del editor.

```lua title="init.lua"
vim.pack.add({
  { src = "https://github.com/catppuccin/nvim", name = "catppuccin" },
  { src = "https://github.com/echasnovski/mini.nvim" },
})

-- El código del plugin ya se puede usar en la línea siguiente
require("mini.surround").setup({})
```

Tres claves en una spec, y ya está: `src` (la URL, cualquier cosa que acepte `git clone`), `name` (el nombre del directorio, por defecto el del repositorio) y `version`:

- Sin `version`: sigue la rama por defecto del repositorio.
- `version = "main"`: una rama, una etiqueta o un hash de commit concretos.
- `version = vim.version.range("1.0")`: la mayor etiqueta semver dentro del rango. Solo funciona si el repositorio publica etiquetas del estilo `v1.2.0`.

<Callout type="info" title="Dónde deja los plugins y qué necesita">
`vim.pack` clona dentro de `site/pack/core/opt`, en el directorio de datos de Neovim, y asume que **todo lo que hay ahí lo gestiona él**. Necesita el ejecutable `git` en el PATH, igual que cualquier otro gestor. Si algún día lo abandonas no pierdes nada: lo que queda en disco son repositorios de Git normales.
</Callout>

<Callout type="warn" title="Marcado como experimental, usable a diario">
La documentación de `vim.pack` sigue etiquetándolo como experimental, con la coletilla de que es lo bastante estable para el día a día. Traducción práctica: úsalo, pero cuenta con que algún detalle de la API pueda afinarse en versiones futuras. No es un motivo para no empezar; sí lo es para leer las notas de cada release antes de actualizar Neovim.
</Callout>

Después de añadir un plugin nuevo, reinicia. En 0.12 no hace falta salir al terminal: `:restart` levanta la sesión otra vez con el código recién instalado.

## El lockfile nativo

Aquí está el argumento que faltaba para tomarse en serio el gestor integrado. `vim.pack` mantiene un lockfile en `~/.config/nvim/nvim-pack-lock.json` (el directorio de config, junto a tu `init.lua`) con la revisión exacta de cada plugin.

<Cards>
  <Card icon="🔒" title="Versiónalo con la config">
    Trátalo como una parte más de tu configuración: al repositorio de Git, igual que el `init.lua`.
  </Card>
  <Card icon="🧬" title="Manda sobre la spec">
    Si el lockfile existe, la primera llamada a `vim.pack` instala **a la revisión del lockfile**, no a lo que resolvería `version`. Otra máquina, mismos commits.
  </Card>
  <Card icon="✋" title="No se edita a mano">
    Lo escribe el editor. Se repara solo si se corrompe, e incluso si lo borras entero se regenera con lo que haya en disco.
  </Card>
</Cards>

### Actualizar

```lua
vim.pack.update()                          -- todos los plugins
vim.pack.update({ "mini.nvim" })           -- solo uno
vim.pack.update(nil, { offline = true })   -- mirar lo instalado sin descargar nada
```

`vim.pack.update()` descarga los cambios y abre un **buffer de confirmación** en una pestaña aparte con el changelog de cada plugin. Ahí decides: `:write` aplica las actualizaciones, `:quit` las descarta. Dentro del buffer, `]]` y `[[` saltan entre plugins, `K` muestra el detalle de un cambio y `gO` lista la estructura. Después, `:restart` para empezar a usar el código nuevo.

Cada actualización real queda registrada en un fichero de log (`nvim-pack.log`, en el directorio de logs de Neovim), así que siempre puedes reconstruir en qué revisión estabas.

### Volver atrás cuando algo se rompe

```bash
# 1) Recupera el lockfile anterior
git checkout HEAD -- nvim-pack-lock.json
```

```lua
-- 2) Tras :restart, fuerza las revisiones del lockfile
vim.pack.update(nil, { offline = true, target = "lockfile" })
```

Ese `target = "lockfile"` es el equivalente exacto de un `:Lazy restore`: en vez de resolver la versión de la spec, usa lo que dice el lockfile.

### Borrar

```lua
vim.pack.del({ "which-key.nvim" })

-- ¿Qué hay en disco que ya no está en tu init.lua?
vim.iter(vim.pack.get())
  :filter(function(p) return not p.active end)
  :map(function(p) return p.spec.name end)
  :totable()
```

Quita primero la spec del `init.lua` —si no, se reinstala en el siguiente arranque—, reinicia y entonces borra.

## Qué aporta lazy.nvim que el gestor nativo no

Que `vim.pack` sea suficiente para la mayoría no lo convierte en sustituto de todo. Esto es lo que lazy sigue haciendo mejor:

<Cards>
  <Card icon="🦥" title="Carga perezosa declarativa">
    `event`, `ft`, `cmd` y `keys` en una línea. `vim.pack` tiene una opción `load` que admite una función, pero entonces la lógica de cuándo cargar la escribes tú, evento a evento.
  </Card>
  <Card icon="🧩" title="El DSL de specs">
    `opts` que se fusionan entre archivos, importar un directorio entero, sobrescribir la spec de un plugin desde otro fichero. Es lo que hace posible una distribución.
  </Card>
  <Card icon="🕸️" title="Grafo de dependencias">
    `dependencies` garantiza el orden de carga. Con el gestor nativo el orden es el de tus llamadas: correcto, pero manual.
  </Card>
  <Card icon="🎛️" title="UI y perfilado">
    `:Lazy` para instalar y revisar, `:Lazy profile` para ver qué plugin te cuesta el arranque. El nativo no tiene panel.
  </Card>
</Cards>

Los hooks de compilación son el caso más ilustrativo. En lazy es una clave de la spec (`build = ":TSUpdate"`); con `vim.pack` es un autocomando que tú enganchas:

```lua title="lua/config/pack-hooks.lua"
vim.api.nvim_create_autocmd("PackChanged", {
  callback = function(ev)
    -- kind es "install", "update" o "delete"
    if ev.data.spec.name == "un-plugin-con-make" and ev.data.kind ~= "delete" then
      vim.system({ "make" }, { cwd = ev.data.path })
    end
  end,
})
```

Se puede, y no es difícil. Pero son diez líneas tuyas contra una clave de una tabla: exactamente el tipo de decisión que esta lección quiere que tomes con los ojos abiertos.

## Dónde cae cada plugin

El criterio no es "cuál me gusta más", sino **si el plugin necesita no estar cargado**.

| Señal | Lado |
|---|---|
| Lo necesitas en el primer frame (el tema) | `vim.pack` |
| El plugin no admite carga perezosa (`nvim-treesitter` rama `main`) | `vim.pack` |
| Es una librería que otros plugins requieren | `vim.pack` |
| Se configura en dos líneas y no tiene coste medible | `vim.pack` |
| Solo aparece con un comando o una tecla (depurador, vista de diffs) | lazy.nvim |
| Solo aplica a ciertos tipos de archivo | lazy.nvim |
| Tiene dependencias con un orden estricto | lazy.nvim |
| Tiene un paso de compilación no trivial | lazy.nvim |
| Quieres sobrescribir sus `opts` desde otro archivo | lazy.nvim |

Fíjate en el tamaño de cada columna en una config real: la izquierda casi siempre es más larga. Y en 0.12 lo es todavía más, porque las piezas caras de antes —el LSP, el completado, el resaltado— ya no son plugins, sino parte del editor.

<Callout type="tip" title="La carga perezosa no es gratis">
Cada plugin diferido es una regla que puede fallar: un `event` que no dispara, un `ft` que no cubre el tipo de archivo real, un plugin que se carga tarde y se pierde el autocomando al que quería engancharse. Si no sabes decir **en qué momento exacto** debe entrar un plugin, cárgalo siempre y mide. Diferir algo que tarda tres milisegundos no compensa una tarde depurando por qué a veces funciona y a veces no.
</Callout>

## Tus tres primeros plugins

Cada instalación va con las dos vías. Elige una pestaña según dónde hayas decidido que cae ese plugin.

### El tema

<Instalar repo="catppuccin/nvim" nota="Sin la clave name el directorio se llamaría nvim, porque vim.pack usa el nombre del repositorio.">

```lua title="lua/plugins/colorscheme.lua"
return {
  "catppuccin/nvim",

    integrations = {
      treesitter = true,
      native_lsp = { enabled = true },
      which_key = true,
      gitsigns = true,
    },
  },
  config = function(_, opts)
    require("catppuccin").setup(opts)
    vim.cmd.colorscheme("catppuccin")
  end,
}
```

</Fragment>

### Treesitter

<Instalar repo="nvim-treesitter/nvim-treesitter" nota="La rama main exige Neovim 0.12 y NO admite carga perezosa. En lazy va con lazy = false; en vim.pack el problema ni se plantea.">
<Fragment slot="lazy">

```lua title="lua/plugins/treesitter.lua"
return {
  "nvim-treesitter/nvim-treesitter",
  branch = "main",
  lazy = false,          -- main no soporta carga perezosa
  build = ":TSUpdate",
  config = function()
    require("nvim-treesitter").install({
      "lua", "vim", "vimdoc", "c", "rust", "markdown",
    })
  end,
}
```

</Fragment>
<Fragment slot="pack">

```lua title="init.lua"
vim.pack.add({
  { src = "https://github.com/nvim-treesitter/nvim-treesitter", version = "main" },
})

require("nvim-treesitter").install({
  "lua", "vim", "vimdoc", "c", "rust", "markdown",
})
```

</Fragment>
</Instalar>

El plugin hace una sola cosa: descargar parsers. El resaltado lo enciende Neovim:

```lua title="lua/config/treesitter.lua"
vim.api.nvim_create_autocmd("FileType", {
  pattern = { "lua", "c", "rust", "markdown" },
  callback = function()
    vim.treesitter.start()
  end,
})
```

<Callout type="warn" title="Casi todo lo que hay escrito sobre nvim-treesitter está muerto">
La rama `main` es una **reescritura incompatible**. El módulo `nvim-treesitter.configs` ya no existe, y con él desaparecieron `ensure_installed`, `highlight`, `indent` e `incremental_selection`. La rama `master` sigue publicada pero está congelada y solo sirve para Neovim 0.11. Si un tutorial te enseña `require("nvim-treesitter.configs").setup(...)`, está escrito para la rama muerta. Lo exprimimos bien en la lección 2.3.
</Callout>

<PluginCard name="nvim-treesitter" repo="nvim-treesitter/nvim-treesitter" tag="core" icon="🌳">
Instalador de parsers y proveedor de queries. La base del resaltado moderno y de la edición por estructura.
</PluginCard>

### which-key

<Instalar repo="folke/which-key.nvim" nota="Caso de libro para lazy.nvim: no hace falta hasta que pulsas leader, y VeryLazy lo saca por completo del arranque.">
<Fragment slot="lazy">

```lua title="lua/plugins/which-key.lua"
return {
  "folke/which-key.nvim",
  event = "VeryLazy",   -- tras el arranque, sin frenar el inicio
  opts = {
    preset = "modern",
  },
}
```

</Fragment>
<Fragment slot="pack">

```lua title="init.lua"
vim.pack.add({ { src = "https://github.com/folke/which-key.nvim" } })

require("which-key").setup({ preset = "modern" })
```

</Fragment>
</Instalar>

Reinicia, pulsa `<leader>` (espacio) y espera medio segundo: aparece el menú con los `desc` que escribiste en la lección anterior.

<Callout type="info" title="Diferir con el gestor nativo, si de verdad quieres">
En la vía nativa no existe `VeryLazy`, pero nada te impide escribir el retardo tú:

```lua
vim.api.nvim_create_autocmd("BufReadPre", {
  once = true,
  callback = function()
    vim.pack.add({ { src = "https://github.com/folke/which-key.nvim" } })
    require("which-key").setup({ preset = "modern" })
  end,
})
```

Funciona, y para uno o dos plugins es razonable. Para veinte, eso es literalmente reimplementar lazy.nvim a mano — y ahí es donde lazy deja de ser opcional.
</Callout>

<PluginCard name="which-key.nvim" repo="folke/which-key.nvim" tag="core" icon="⌨️">
Descubre y recuerda atajos leyendo los `desc` de tus keymaps. Imprescindible cuando tu config crece.
</PluginCard>

<Callout type="warn" title="El presupuesto de teclas empieza hoy">
Antes de que la config crezca, fija cuatro reglas y no las rompas. `<C-Space>` y `<Tab>` son del autocompletado —el nativo de 0.12 y también el de blink.cmp o nvim-cmp—, así que no los mapees a nada más. `s` y `S` son verbos nativos de Vim, y además `s` es el prefijo de operador de `mini.surround`: no se los cedas a un plugin de saltos. Los saltos van en `]` y `[`; tus acciones, detrás de `<leader>`. Un conflicto de teclas no da error: simplemente algo deja de responder y crees que el plugin está roto.
</Callout>

## La configuración híbrida

Esta es la forma que recomienda esta guía: el gestor nativo lleva el grueso, y lazy.nvim entra solo para lo que gana con carga perezosa.

```lua title="init.lua"
-- 1) leader antes que nada
vim.g.mapleader = " "
vim.g.maplocalleader = " "

require("config.options")
require("config.keymaps")
require("config.autocmds")

-- 2) Lo que siempre está: gestor nativo
vim.pack.add({
  { src = "https://github.com/catppuccin/nvim", name = "catppuccin" },
  { src = "https://github.com/nvim-treesitter/nvim-treesitter", version = "main" },
  { src = "https://github.com/echasnovski/mini.nvim" },
}, { load = true })

require("config.tema")
require("config.treesitter")
require("mini.surround").setup({})
require("mini.pairs").setup({})

-- 3) Lo que gana con carga perezosa: lazy.nvim
require("config.lazy")
```

```lua title="lua/config/lazy.lua"
local lazypath = vim.fn.stdpath("data") .. "/lazy/lazy.nvim"
if not vim.uv.fs_stat(lazypath) then
  vim.fn.system({
    "git", "clone", "--filter=blob:none", "--branch=stable",
    "https://github.com/folke/lazy.nvim.git", lazypath,
  })
end
vim.opt.rtp:prepend(lazypath)

require("lazy").setup({
  spec = { { import = "plugins" } },
  performance = {
    reset_packpath = false,   -- vim.pack necesita site en el packpath
    rtp = { reset = false },  -- y sus plugins ya están en el runtimepath
  },
  checker = { enabled = true, notify = false },
  ui = { border = "rounded" },
})
```

En `lua/plugins/` dejas solo lo que de verdad se difiere: which-key con `event`, el depurador con `cmd`, los plugins por tipo de archivo con `ft`. Un archivo por plugin, como antes.

<Callout type="dios" title="Las tres reglas de la convivencia">
Que los dos gestores se lleven bien depende de tres detalles nada obvios, y los tres se explican por lo mismo: lazy.nvim optimiza el arranque **tomando el control del runtimepath**.

1. **`vim.pack.add()` antes de `require("lazy").setup()`.** Si un plugin gestionado por lazy necesita algo del lado nativo, tiene que estar ya en el runtimepath.
2. **`load = true` explícito en el `add`.** lazy pone `loadplugins` a `false` porque carga los plugins él mismo. Dentro de `init.lua`, `vim.pack.add` por defecto solo añade el directorio al runtimepath y deja los archivos `plugin/` para la carga automática del arranque… que lazy acaba de desactivar. Con `load = true` se cargan en el momento del `add` y el problema desaparece.
3. **Desactiva los dos reseteos de rendimiento de lazy.** `reset_packpath` deja el `packpath` reducido a `$VIMRUNTIME`, y entonces `vim.pack` ya no encuentra sus propios plugins; `rtp.reset` reescribe el runtimepath entero con una lista fija, tirando los directorios que `vim.pack` acababa de añadir. Pagas unos milisegundos de arranque por tener las dos vías vivas.
</Callout>

### Qué pierdes y qué ganas

| Pierdes | Ganas |
|---|---|
| Dos lockfiles que versionar y dos comandos de actualización | El grueso de tu config no depende de ningún plugin externo |
| `:Lazy profile` solo mide lo que gestiona lazy (para el resto, `nvim --startuptime`) | Menos capas entre tú y el runtimepath: los fallos se leen mejor |
| Los reseteos de runtimepath de lazy, que ahorran unos milisegundos | El gestor se actualiza con el editor, no por su cuenta |
| Ejemplos: casi toda la documentación de internet asume lazy para todo | Tus specs de lazy dejan de ser 40 líneas con `event = "VeryLazy"` copiado sin pensar |

## El flujo de trabajo

<Callout type="dios" title="El mejor gestor es el que te lleva a tener menos plugins">
Durante años la conversación fue "qué gestor usas", y era una conversación de fontanería disfrazada de identidad. Lo que 0.12 cambia no es quién clona los repos: es cuántos repos necesitas clonar. Con el gestor, el LSP y el completado dentro del editor, una configuración seria de 2026 puede vivir con un puñado de plugins en vez de cuarenta — y cada plugin que no instalas es una dependencia que no se rompe, una actualización que no revisas y un conflicto de teclas que no depuras. Usa `vim.pack` para el grueso, lazy.nvim donde aporte, y mide antes de añadir nada.
</Callout>

<Reto title="Tu primer setup con plugins">
1. Instala el tema con `vim.pack` y comprueba en `vim.pack.get()` que aparece con su revisión.
2. Añade `nvim-pack-lock.json` a tu repositorio de config y haz commit.
3. Monta lazy.nvim con los dos reseteos desactivados y `which-key` como única spec.
4. Reinicia con `:restart`, pulsa `<leader>` y confirma que which-key muestra tus atajos.
5. Ejecuta `vim.pack.update()` y descarta los cambios con `:quit` para ver la red de seguridad.
6. Coge tres plugins que quieras instalar y decide, por escrito, en qué lado cae cada uno y por qué.

Con esto dominas el ciclo instalar → fijar versión → cargar. En el Nivel 2 lo usaremos para construir el IDE.
</Reto>
