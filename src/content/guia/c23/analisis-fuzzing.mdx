<Lead>
Los sanitizers cazan bugs cuando el código se ejecuta con una entrada dada. Pero ¿y los bugs en caminos que tus tests no recorren? Para eso están dos familias complementarias: el análisis estático, que examina el código sin ejecutarlo, y el fuzzing, que bombardea tu programa con millones de entradas para encontrar las que lo rompen.
</Lead>

<Objetivos>

- Análisis estático: encontrar bugs sin ejecutar.
- Valgrind para memoria en tiempo de ejecución.
- Fuzzing: descubrir entradas que rompen.
- Cómo se complementan las tres técnicas.

</Objetivos>

## Análisis estático

Un analizador estático lee tu código y razona sobre todos los caminos posibles, señalando bugs potenciales sin ejecutar nada:

```bash
# el analizador integrado en GCC
gcc -std=c23 -fanalyzer -Wall prog.c

# clang-tidy: cientos de checks (bugs, estilo, modernización)
clang-tidy prog.c -- -std=c23

# cppcheck: analizador dedicado, fácil de integrar
cppcheck --enable=all prog.c
```

Detectan cosas que el compilador normal no: dobles frees en ciertos caminos, punteros nulos condicionales, fugas en ramas de error, uso de memoria liberada. Como examinan **todos** los caminos (no solo los que tus tests ejecutan), encuentran bugs latentes.

## Valgrind

Valgrind (su herramienta Memcheck) ejecuta tu programa en una máquina virtual que vigila cada acceso a memoria. Más lento que ASan pero no requiere recompilar y detecta cosas distintas:

```bash
valgrind --leak-check=full ./prog
# informa de accesos inválidos, memoria no inicializada y fugas exactas
```

## Fuzzing: el que encuentra lo que no imaginaste

El **fuzzing** alimenta tu programa con entradas generadas automáticamente —millones, guiadas por cobertura de código— buscando las que provocan un crash o un fallo de sanitizer. Descubre casos límite que ningún humano escribiría como test:

```c
// objetivo de libFuzzer: recibe datos arbitrarios y los procesa
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parsear(data, size);   // tu función bajo prueba
    return 0;
}
```

```bash
clang -std=c23 -fsanitize=fuzzer,address parser_fuzz.c -o fuzzer
./fuzzer          # genera entradas sin parar hasta encontrar un crash
```

<Callout type="dios" title="El fuzzing encuentra los bugs que tú no puedes imaginar">
Esta es la técnica que más humilla y más protege. Tú escribes tests para los casos que se te ocurren; el fuzzer prueba los que **no** se te ocurren: una cadena de 4 GB, bytes nulos en medio, un número negativo donde esperabas positivo, entradas maliciosamente formadas. Combinado con ASan, cada entrada que dispara un error de memoria queda registrada con el input exacto que lo provoca. Proyectos críticos —navegadores, librerías de parsing, criptografía— fuzzean sin parar (Google ejecuta OSS-Fuzz sobre miles de proyectos 24/7) y encuentran miles de vulnerabilidades que ninguna revisión humana habría visto. Si escribes código que procesa entrada no confiable —un parser, un decodificador, un formato de red—, el fuzzing no es opcional: es la diferencia entre "creo que es seguro" y "lo he bombardeado con millones de entradas y aguanta".
</Callout>

## Las tres técnicas se complementan

<Cards>
  <Card icon="🔬" title="Estático">
    Sin ejecutar. Cubre todos los caminos, encuentra bugs latentes. Puede dar falsos positivos.
  </Card>
  <Card icon="🧪" title="Sanitizers + tests">
    Ejecutando tus casos. Preciso y sin falsos positivos, pero solo los caminos que tus tests recorren.
  </Card>
  <Card icon="💥" title="Fuzzing">
    Ejecutando entradas automáticas. Encuentra los caminos que no imaginaste. Necesita tiempo de cómputo.
  </Card>
</Cards>

<Reto title="Ataca tu propio código">
1. Pasa `gcc -fanalyzer` y `cppcheck --enable=all` sobre un programa tuyo y lee los avisos.
2. Ejecuta un programa con fugas bajo `valgrind --leak-check=full`.
3. Escribe un pequeño `LLVMFuzzerTestOneInput` para una función de parsing y lánzalo con `-fsanitize=fuzzer,address`.
4. Deja el fuzzer corriendo unos minutos: ¿encuentra alguna entrada que no habías previsto?
</Reto>
