## El DAG que ejecutas cada día

Cuando un gestor de paquetes instala dependencias, cuando un build decide qué recompilar o cuando un motor de reactividad decide qué recalcular, todos hacen lo mismo: construyen un **grafo dirigido acíclico** y lo recorren en **orden topológico**. La palabra «acíclico» no es decorativa: es la condición que hace posible que exista un orden válido, y su ausencia es exactamente el mensaje de error `circular dependency detected`.

```ts
// Esto es un orden topológico, aunque el nombre no aparezca por ningún lado.
function resolver(tareas: Map<string, string[]>): string[] {
  const hecho = new Set<string>()
  const enCurso = new Set<string>()
  const salida: string[] = []

  const visitar = (t: string) => {
    if (hecho.has(t)) return
    if (enCurso.has(t)) throw new Error(`ciclo en ${t}`) // el grafo no era un DAG
    enCurso.add(t)
    for (const dep of tareas.get(t) ?? []) visitar(dep)
    enCurso.delete(t)
    hecho.add(t)
    salida.push(t)
  }

  for (const t of tareas.keys()) visitar(t)
  return salida
}
```

Lo que el nivel 33 añade a este código que ya sabías escribir es la parte que no se ve: que el orden topológico **no es único** y que por eso dos ejecuciones del build pueden dar órdenes distintas y ambos ser correctos; que el **camino crítico** del grafo es la cota inferior del tiempo de compilación por muchos núcleos que le eches; y que detectar el ciclo con un conjunto `enCurso` es la clasificación de aristas del DFS, no un truco.

## El orden parcial que llevas ignorando

Dos usuarios editan el mismo documento sin conexión. Al reconectar, ¿qué edición fue antes? La pregunta tiene trampa: **ninguna**, y no por falta de información sino porque el «antes» no está definido entre ellas. Eso no es un fallo del sistema, es la propiedad de un **orden parcial**: hay pares de elementos que sencillamente no son comparables.

| enfoque | qué asume | qué rompe |
| --- | --- | --- |
| ordenar por reloj de pared | que existe un tiempo global | dos relojes desfasados, ediciones perdidas |
| último en llegar gana | que el orden de llegada es el orden real | el que tenía peor red pierde su trabajo |
| orden parcial explícito | que hay pares incomparables | nada: modela la realidad |

El nivel 14 le pone nombre —incomparabilidad, diagrama de Hasse— y el nivel 15 da la salida: si el estado vive en un **semirretículo** y la fusión es su supremo, la convergencia deja de depender del orden. Es literalmente el teorema que sostiene los CRDT.

<Callout type="info" title="Tres propiedades y ya converge">
La fusión de dos réplicas converge si es conmutativa, asociativa e idempotente. Conmutativa para que el orden de llegada no importe, asociativa para que el agrupamiento no importe, idempotente para que recibir el mismo mensaje dos veces no importe. Esas tres condiciones definen un semirretículo de unión, y son el contenido entero del nivel 15. Nótese lo que no exige la lista: ni relojes sincronizados, ni entrega ordenada, ni entrega exactamente una vez.
</Callout>

## El palomar dentro de tu mapa de hash

Un `HashMap` con $2^{64}$ posibles hashes y un conjunto de claves infinito **tiene** colisiones. No «puede tener»: tiene, garantizado, y no hay función hash lista que lo evite. La razón es el **principio del palomar**: si metes más objetos que cajas, alguna caja repite. De ahí sale que toda implementación seria lleve una estrategia de colisión —encadenamiento, sondeo lineal— y de ahí sale también que un `hashCode` que devuelva siempre `1` sea correcto pero catastrófico.

El mismo principio, aplicado a otro dominio, demuestra algo que suena imposible: **no existe un compresor sin pérdida que reduzca todos los archivos**. Si comprimiera cada archivo de $n$ bits a menos de $n$ bits, dos archivos distintos acabarían con la misma salida y la descompresión sería ambigua. El nivel 22 lo hace en tres líneas.

## La recurrencia que explica la lentitud

La función recursiva ingenua para Fibonacci es correcta y es inservible, y la explicación no es «la recursión es lenta» sino una recurrencia concreta:

$$
T(n) = T(n-1) + T(n-2) + 1
$$

Esa relación crece como $\varphi^n$ con $\varphi \approx 1{,}618$, así que $T(50)$ ronda los mil millones de llamadas. El nivel 25 enseña a resolver esa recurrencia con la ecuación característica y a leer el resultado sin ejecutarlo. El nivel 26 hace lo propio con el patrón de dividir el problema, donde el teorema maestro te dice de un vistazo si el coste está dominado por la partición o por las hojas.

```ts
// Correcto y catastrófico: T(n) = T(n-1) + T(n-2) + 1
const fib = (n: number): number => (n < 2 ? n : fib(n - 1) + fib(n - 2))

// Correcto y lineal: la misma recurrencia, evaluada una sola vez por término.
function fibIterativo(n: number): number {
  let [a, b] = [0, 1]
  for (let i = 0; i < n; i++) [a, b] = [b, a + b]
  return a
}
```

## La equivalencia que firma tu `equals`

Cuando implementas igualdad, estás declarando una **relación de equivalencia**, y el contrato que casi todos los lenguajes exigen —reflexiva, simétrica, transitiva— no es burocracia: es la definición exacta de esa estructura. El teorema que la acompaña dice que toda relación de equivalencia parte el conjunto en **clases disjuntas**, y de ahí sale el requisito que se olvida siempre: si dos objetos son iguales, su hash debe coincidir, porque el mapa agrupa por clase y no por objeto.

Romper la transitividad produce el bug más desconcertante del catálogo: `a.equals(b)` y `b.equals(c)` ciertos, `a.equals(c)` falso, y una colección que contiene un elemento y a la vez no lo contiene según por dónde se pregunte. El nivel 13 explica por qué la estructura lo impide y qué se rompe cuando la violas.

## Lo que cambia al reconocerlo

Reconocer la estructura no te hace escribir menos código; te hace escribir menos código equivocado y, sobre todo, te ahorra buscar soluciones que un teorema ya declaró imposibles.

| lo que hacías | lo que hace quien reconoce la estructura |
| --- | --- |
| probar combinaciones hasta que el test pase | contar el espacio primero y descubrir que son $2^{20}$ |
| buscar una función hash sin colisiones | asumir colisiones y elegir bien la estrategia |
| ordenar eventos concurrentes por timestamp | modelar el orden parcial y fusionar por supremo |
| añadir `if` hasta cubrir los casos | negar el cuantificador y ver los casos que faltan |
| medir el algoritmo recursivo con un `console.time` | escribir su recurrencia y resolverla |

<Callout type="warn" title="El riesgo contrario también existe">
Reconocer estructuras engancha, y al principio se ven grafos donde hay una lista de tres elementos. La matemática discreta paga cuando el problema tiene tamaño o cuando la corrección importa; para tres casos enumerados a mano, escribir el modelo formal cuesta más de lo que ahorra. El criterio útil: si puedes enumerar todos los casos en una tarde y estás seguro de no olvidar ninguno, enuméralos. Si no puedes, o si no estás seguro, es cuando la estructura empieza a pagar.
</Callout>

<Callout type="dios" title="La matemática no se aplica al código: el código ya era matemática">
La forma habitual de contar esta relación —primero se aprende la teoría y luego se aplica a la práctica— describe mal lo que ocurre y por eso motiva mal. Lo que ocurre es más raro y más interesante: los objetos matemáticos no se aplican al programa desde fuera, ya estaban dentro desde que alguien escribió la primera línea. El grafo de dependencias existía antes de que nadie lo llamara DAG; la relación de equivalencia estaba operando en tu `equals` aunque no supieras su nombre; el palomar decidía tus colisiones sin pedirte permiso. Lo que la teoría añade no es una capa nueva sobre el código, es la capacidad de *ver* lo que el código ya hacía, y esa visión cambia el tipo de pregunta que uno se atreve a hacer. Sin ella, ante un comportamiento raro se pregunta «¿qué línea lo causa?» y se depura; con ella, se pregunta «¿qué propiedad estoy violando?» y se razona, que es una pregunta más barata y con mejor respuesta. La consecuencia práctica de todo el temario es esa mudanza en el tipo de pregunta: dejas de tratar el programa como una caja opaca que hay que sondear con `console.log` y empiezas a tratarlo como un objeto con propiedades que se pueden afirmar o negar. Los programadores que parecen adivinar dónde está el bug no adivinan: han reconocido la estructura y saben qué es lo único que podía haber fallado.
</Callout>
